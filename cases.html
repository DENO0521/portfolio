BUSINESS → APPLICATION

竞品情报与销售支持平台

统一比较口径，分开资料确认与话术发布

业务问题
多个部门重复收集竞品资料，比较口径不一致；销售查阅时难以识别内容依据、确认状态和资料缺口。
我的贡献
建立3组14个固定标签，分别组织管理比较、销售查阅和维护入口；通过来源、状态和草稿隔离，区分资料确认与正式发布。
交付价值
把分散资料转成统一标签下可比较、可维护并呈现来源说明的应用，让业务人员查阅时能够区分已确认、待确认和缺失内容。
职责分工
项目主导、产品设计与独立开发部署；已对接使用流程，OD负责组织推广。
实现思路与关键取舍
多来源竞品资料
→
14标签 / 来源 / 状态
→
比较、查询与维护入口

实现说明

Flask与SQLite为个人履历记载的技术栈，Codex与WorkBuddy用于辅助开发。历史页面可检查标签、资料状态和查询路径；本案例重点展示信息治理与应用交付，运行时模型调用及其效果尚未形成可展示记录。

关键取舍

“资料已确认”和“话术已发布”分别管理。待核实资料可以暴露缺口，不能自然进入正式销售话术。

Flask · SQLite · HTML（个人履历技术栈）；Codex / WorkBuddy辅助开发

AI 试卷分析与课程推荐

让分析结果对齐已有课程资源

业务问题
模型自由拆分的知识点难以对应既有课程，试卷分析结果无法稳定衔接可交付的课程资源。
我的贡献
将题号与知识库作为对应关系，定义小题、分值、答案等字段和样板；先交付分析，再补课程推荐，协调业务、教研和研发。
交付价值
把“生成分析”转成能接入既有课程的产品与数据规则，让教研资源准备和研发实现有共同的字段、样板与版本范围。
职责分工
负责产品取舍、PRD、数据标准与交付协调；系统由研发团队实现。
实现思路与关键取舍
题号与作答数据
→
知识库 / 已有课程映射
→
分析与课程衔接

实现说明

产品设计用题号、知识库及已有课程的对应关系约束推荐范围。原表展示字段与资源映射；系统工程实现由研发承担，页面依据现有材料说明产品与数据规则。

关键取舍

先保证分析和数据可用，再推进课程推荐；通过固定字段与教研样板，减少自由知识点名称与真实课程之间的脱节。

PRD · 字段样板 · 题号与知识库映射 · 分期交付

效果口径PRD与知识库证明设计思路；与具体上线版本的关联仍待补证。原型分数为示例，不用于说明学生提分、推荐准确率或招生效果。
